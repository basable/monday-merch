# 02: design

Brand assets and proofs. No lifecycle: a proof waits for a person's decision, but nothing polls, schedules or drives another system on its behalf, and the quote's own flow already tracks that wait. So this is a plain executor (Directive §1). Directive §2 binds every table, §6 the call, §7 every message.

**Written for the recommended round 1 answer: Design Studio `later`.** Consultants and designers create artwork in their own tools and upload the result. If the Studio is included, this file gains design documents, versions and templates.

## Tables

**`brand_profile`** is one row per company (`company_id`): `colours`, `fonts`, `guidelines`, `updated_at`.

**`brand_asset`** is an uploaded logo, font or image: `company_id`, `kind`, `filename`, `object_key`, `mime_type`, `size_bytes`, `created_at`, `confirmed_at`, `deleted_at`. A row is created with the presigned URL and confirmed once a HEAD shows the object exists and fits the limits.

**`proof`** is one version of a design for one quote line: `subject_name` (the caller's name, `quote:<id>`), `line_ref`, `version`, `preview_key`, `artwork_key`, `print_spec` (method, area, colours, size), `created_by`, `created_at`, `approved_at`, `approved_by`.

## Invariants

- A proof version never changes. A correction is a new `version`.
- `approved_at` is one-way. `ApproveProofsRequest` names exact versions and is idempotent, so a retry changes nothing.
- A quote can only be signed if each line has a proof. `order` checks this before signing.
- Customers see proofs through `order` (`GetQuote` authorises, then calls `ListProofsRequest`). This nanoservice therefore never decides who may see a quote.

## Uploads and buckets

Everything here is in the **private bucket**: `design/assets/<company>/...`, `design/proofs/<subject>/...`. The browser uploads with a presigned PUT moved onto `S3_PRIVATE_URL`, and reads with a short-lived presigned GET.

Accepted types match what designers need: SVG, PDF, AI, PSD, PNG, JPG. Size is capped at 100 MiB. These files come from strangers and designers open them on their own machines, so GETs are presigned with `Content-Disposition: attachment` and uploaded SVG is never rendered inline. Preview images are generated by the designer's tool, never on the server.

## External calls

**`delete_object`** on `object_storage`, strategy `idempotent`: deleting an absent object succeeds, so a retry is safe. The simulator models delete-then-delete and ack loss. Presigning sends nothing and HEAD is a read, so neither is an adapter (Directive §6).

## Schedules

`purge_orphan_uploads` runs every 24h. It finds `brand_asset` rows older than 24h with no `confirmed_at`, deletes the object and then the row. It reads the table and never lists the bucket, because bucket listings cost more.

## Messages and API

`DesignService`: `GetBrandProfile`, `UpdateBrandProfile`, `ListBrandAssets`, `CreateAssetUpload`, `ConfirmAssetUpload`, `DeleteBrandAsset`. `CreateProof` and `ListProofs` require a staff role.

Internal, from `order`: `ListProofsRequest`, `ApproveProofsRequest`, `GetApprovedArtworkRequest` (presigned artwork links for a purchase order, valid 7 days).

## Binding Directive sections

§1, §2 (tables), §6 (`delete_object`), §7 (messages).

## Tests

- `effecttest` audit for `delete_object` in `tests/effects_audit.rs`.
- Company A cannot read, confirm or delete company B's assets.
- `ConfirmAssetUpload` refuses a missing object, one over the limit and a wrong type.
- `ApproveProofsRequest` twice leaves one approval, and a proof version cannot be overwritten.
- `purge_orphan_uploads` keeps confirmed assets and removes only stale unconfirmed ones.
